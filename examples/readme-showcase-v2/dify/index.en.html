How do Dify’s three layers work?

Uploading a file does not finish a knowledge index. Online chat does not always go through a task queue. Follow both paths across real service and storage boundaries.

What does this diagram include—and leave out?
  • Scope: self-hosted Dify, local text files, high_quality paragraph indexing, basic AppMode.CHAT, a configured and selected internal dataset with semantic retrieval, and successful paths.
  • Three data forms: original files in file storage; metadata and chunks in SQL; vector indexes in the vector database. PostgreSQL and Weaviate are the choices shown here, not the only supported stores.
  • The indexing Worker is a separate Celery process. Chat and RAG code within the API are not additional microservices.
  • A Redis query-embedding cache hit skips the embedding-model call. Dataset routing may call an LLM first, so the edges are not a strict execution order.
  • Model calls are traced only to the Plugin Daemon HTTP interface. Its separate repository and specific provider plugins have not been reviewed; downstream calls are not drawn as verified relationships.
  • Workflow, Chatflow, Agent, knowledge pipelines, multimodal processing, reranking, errors, retries, Web server hosting and other database/cache accesses are excluded.
